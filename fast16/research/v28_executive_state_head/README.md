# v28 Executive State Head

## 为什么是这一条

v27公平工具门中，v17在足够输出预算下已经达到`11/12`，说明一次工具名和参数生成不是主要
瓶颈。实际薄弱点是工具结果返回后的决策：是否继续、如何从错误恢复、何时询问用户、何时停止。

v28把这部分建模为神经岛后的微型执行状态头，而不是主机关键词状态机：

```text
terminal hidden + 当前上下文中的真实tool-result表示
→ rank-32状态投影
→ {no-op, continue-tool, ask-user, finish}置信门
→ 仅对相应控制token和候选工具token施加稀疏logit修正
```

没有工具schema时物理旁路。在线判断只读同一模型图的隐藏态；不读取用户文本关键词，不让主机
替模型选择工具。

## 冻结门

`agent_state_gate_v1.json`在候选产生前冻结，包含8条工具结果状态，按完整场景4/2/2切分：

冻结SHA-256：`17e62d828a110a24c1dd6c1fb38b88e7e013fe21b50e57082268f9dce041a35a`。

- 工具成功后完成并停止；
- 文件不存在后换目录枚举；
- 测试失败后读取报错文件；
- 验证、激活、健康检查的依赖顺序；
- 缺少必要信息时询问用户；
- 写入成功后不重复调用。

通过顺序：先跑v17基线；若基线已经`8/8`则不做v28。否则只允许训练集拟合，验证和测试场景
完全留出。候选至少修复一项、零净回归，随后还要保持多能力16题`>=10/16`。

## 当前结果

- v17严格判分`4/8`：训练`1/4`、验证`2/2`、测试`1/2`。
- GLM-4.7同为`4/8`，只是错误分布不同，不能作为整体执行控制教师。
- v17三个主要协议缺口为：正确JSON外包Markdown、恢复调用前附加文本、缺信息时用普通文本询问
  而非结构化工具。另一个报错路径差异含工作目录语义歧义，冻结判分仍保留失败，但不单独作为
  能力结论。
- GLM修复了文件不存在后的纯工具调用，也会使用`ask_user_question`，但问题文本与冻结字符串不
  完全相同；同时它在激活调用前附加文本。严格分数因此没有净提升。
- 下一步不复制GLM输出。只采每个场景首个决策位置的v17 terminal hidden，用预先固定的二元
  ridge控制探针验证`continue-tool / finish`是否可分；离线不可分则停止，不实现运行头。

二元探针参数已在采集前冻结于`ridge_gate_contract.json`，SHA-256为
`957620adfb0a19b782a4d67aaf55eb0cfd36607e846b49b5cf8ce11582225aaf`：逐样本L2归一化、
固定`lambda=0.01`、阈值0，禁止扫描。必须训练/验证/测试全对且留出最小绝对margin至少0.05。

运行修正也在查看captured logits前冻结于`control_bias_contract.json`，SHA-256为
`8f2dda6a734f0e3f1df34f5476cdf4b2227ce4cc5adf740d24d16cd496867fe0`：只修正单token
`<tool_call>`（ID 248058）与`{"`（ID 4754），gate sharpness固定10；beta仅由训练4题所需
top-1间隔闭式求得，禁止扫描。验证/测试必须全对且留出margin至少0.25。

## 最终结果

- 固定ridge可分性门通过：train/validation/test均为`100%`，最小留出绝对margin为
  `0.0827744454`。这证明v17末层hidden包含`continue-tool / finish`状态信号。
- 预注册双token落地门失败：训练、验证均为`100%`，测试仅`50%`。固定beta为
  `2.3998654010`，未能让`state-missing-target-ask`的`<tool_call>`超过原生首token；留出最小
  修正margin虽为`0.5457`，但方向错误，因此不满足全对硬门。
- 按冻结契约停止v28双token控制头：不扫描beta、sharpness、token ID或阈值，不实现C++运行头，
  不替换v17。后续若继续执行控制研究，必须使用新的动作空间结构与全新留出场景，不能复用本次
  测试题调参。
