# v19 输出头降本算法推演

## 先决结论

当前 v19.1 稠密双头在独立 60-token 冒烟上平均 NLL **回归** `+0.008770`，任务胜负 `5:5`，
tool 组均值回归 `+0.012139`，并且所有 LOTO 方向不为改善。按既有评估契约，输出头降本只能是
纸面候选，不能绕过能力门进入产品路径。

如果稠密输出头以后在冻结多能力门上通过，推荐唯一方案是：

> **中心化低秩侦察头 + 残差范数上界 + 原始 Q6_K 行分页 + 贪心 top-1 证书。**

低秩头只做候选发现，不直接决定 token；最终分数由 v2 包中的原始 Q6_K 行精确计算。无法在
候选行上限内证明 top-1 时，回退现有稠密投影。

## 当前成本基线

记映射行数 `m=131,612`、隐藏宽度 `d=2,048`。当前 v2 输出头：

- Q6_K 映射投影：`m × 1,680 = 221,108,160` 字节；
- `output_norm + mapping` 后包总量：`222,169,248` 字节，即 `211.88 MiB`；
- 稠密投影乘加：`m × d = 269,541,376 MAC/token`；
- 实测 Vulkan compute buffer 从约 `563.30 MiB` 增至 `1,504.44 MiB`；
- 相邻短门速度从代码 `19.51` 降到 `15.86 token/s`，工具从 `17.41` 降到 `13.19 token/s`。

包大小不是 941 MiB compute buffer 增量的全部原因；大词表中间张量、图工作区和后端放置必须
用实现后的 trace 归因，不能把静态 MAC 比例直接写成速度提升。

## 数学形式

对 donor 最终隐藏态 `h` 做原生 output norm。把 v2 的已解码 Q6_K 行记为
`Q ∈ R^(m×d)`，行均值为：

```text
q_bar = mean_rows(Q)
X     = Q - 1 q_bar^T
delta = X h
logit[base_id_i] += alpha * delta_i
```

原实现先算所有 `Qh` 再做零均值；`q_bar^T h` 可用一个 2048 维点积得到，因此中心化本身不需要
计算 m 行。离线对中心化矩阵做截断分解：

```text
X = A B + E
A: m × r, Q8 per-row
B: r × d, F16
rho_i >= ||E_i||_2 + factor_quantization_error_i
```

运行时侦察分数和严格区间为：

```text
s_i   = (A B h)_i
eps_i = rho_i * ||h||_2
delta_i ∈ [s_i - eps_i, s_i + eps_i]
```

当 `alpha >= 0` 时，映射 token 的最终 logit 上界：

```text
U_i = base_logit[base_id_i] + alpha * (s_i + eps_i)
```

未映射 base token 没有 donor 更新，其 base logit 已是精确值。`alpha < 0` 时交换区间端点；首版
可以直接拒绝负 alpha，避免多一条未经验证路径。

## 贪心解码算法

1. 正常计算 base logits 和 donor 的 2048 维最终隐藏态；alpha=0 继续物理旁路。
2. 计算 `z=B h`、全部侦察值 `s=A z`、逐行误差 `eps=rho*||h||` 和上界 `U`。
3. 初始候选取 base mapped top-K 与 `U` top-K 的并集；同时纳入当前精确最高的未映射 base token。
4. 从 host/SSD 的原始 Q6_K 行库把候选行分页到 GPU 行缓存，计算精确中心化 donor delta。
5. 若“已计算候选的最高精确最终 logit”严格高于“所有未计算行的最大 U”以及所有未映射 base
   logit，则该 token 与稠密双头的 greedy top-1 一致，可以提交。
6. 否则按 U 继续扩候选。超过 512 行（默认点）或数值边界过近时，回退稠密头。

对 top-k 可把证书阈值换成已计算候选的第 k 高精确值。对温度采样、top-p 和 teacher NLL，概率
归一化依赖所有行；首版必须回退稠密头，不用未经证明的近似分布。

## 推荐静态点

`output_head_cost_model.py` 给出三个纯算术点。推荐先验证 `r64-c512-cache8192`：

| 点 | 估算 MAC/token | 稠密比例 | 理想 MAC 降幅 | 估算 GPU 常驻 | 512/1024 行全 miss 上传 |
|---|---:|---:|---:|---:|---:|
| r32 / 256 / cache4096 | 4,803,456 | 1.78% | 56.11x | 12.25 MiB | 0.410 MiB |
| **r64 / 512 / cache8192** | **9,604,864** | **3.56%** | **28.06x** | **22.98 MiB** | **0.820 MiB** |
| r96 / 1024 / cache16384 | 14,930,560 | 5.54% | 18.05x | 40.31 MiB | 1.641 MiB |

常驻估算包含 Q8 `A`、逐行 F16 scale、F16 `B`、F16 `rho`、F32 均值行、I64 映射和 Q6_K
行缓存；221.1MB 原始投影仍作为 host/SSD 冷库保留。它不包含 GGML 对齐和图工作区。

推荐 r64 而不是 r32 的原因不是静态成本，而是上界松紧决定回退率。r32 只有在同一冻结 trace
上仍能以不超过 256 行认证绝大多数 token 时才有意义。

## 离线构建

1. 按 v2 行哈希解码固定 Q6_K 数值，计算 `q_bar` 和中心化矩阵；不使用原始 BF16 另造目标。
2. 用 randomized SVD/分块 eigensolver 构建 r64 因子，避免一次物化整张 F32 矩阵。
3. A 做逐行 Q8；B 保存 F16。对因子量化后的实际近似重新计算每行残差范数 `rho_i`。
4. `rho_i` 必须向上舍入并计入 F16/Q8 表示误差；否则 top-1 证书不成立。
5. 运行包记录源 head 哈希、因子哈希、构建精度、rank、误差上界方法和原始行库哈希。

## 验证门

先在稠密 v19 已经通过能力门的同一隐藏态 trace 上离线回放：

- greedy token 与稠密双头 `100%` 一致；任何不一致都是算法错误；
- 至少 `99%` decode 步在 512 行内得到证书；fallback 率 `<=1%`；
- p95 精确行数 `<=512`，p99 `<=1024`；
- 行缓存命中、上传字节、批次数和等待时间逐层/逐步可观察；
- alpha=0 的输出、NLL、图节点和权重加载继续严格旁路；
- 通过上述正确性后，才做一次相邻 128-token A/B；至少恢复稠密输出头损失吞吐的 80%。

若 rank96 仍无法把 fallback 压到 1%，说明谱残差上界太松，这条方案停止，不靠取消证书换速度。

## 为什么不选其他方案

- **静态高频 token 子集**：会永久排除 donor 可能拉升的低频决策 token，无法归因。
- **只做低秩 LM head**：便宜但最终 logit 不再来自原始 Q6_K 行，能力变化与降本误差混在一起。
- **只做 Q6_K 行缓存**：降低常驻权重，不减少每 token 对 131,612 行的稠密计算。
- **词表聚类树**：可以分层搜索，但没有残差上界时仍不能证明与稠密头 greedy 等价。
- **直接截断 softmax**：对 teacher NLL 和采样分布不成立；首版明确稠密回退。

## 实施边界

本组不修改 v19 或 llama.cpp。即使静态模型显示约 28x MAC 降幅，也必须先解决 v19.1 的能力
失败；否则优化的是一个尚未证明有用的分支。
